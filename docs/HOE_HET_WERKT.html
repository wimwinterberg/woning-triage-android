Hoe Woningtriage nu werkt

Een bewoner beschrijft een probleem in de huurwoning. GPT-Live voert het gesprek. De Symfony-backend is de bron van waarheid: die vult LEDO, zoekt het adres op, maakt de samenvatting en legt de melding vast. Het model mag niets “opslaan” totdat de backend dat zegt.

1. Overzicht

Het product is één intake per gesprek. De structuur is LEDO: locatie, element, defect, oorzaak. Daarna postcode + huisnummer, live adreslookup, bevestiging, samenvatting, en pas dan een report. 

flowchart LR
  B["Bewoner"] -->|spraak of typen| A["Android-app"]
  A -->|"REST /api/v1"| API["Symfony API"]
  A <-->|"WebRTC audio + oai-events"| G["GPT-Live"]
  W["live-gateway worker"] <-->|"sideband WSS attach"| G
  W -->|"runAnalysis"| S["IntakeService"]
  API --> S
  S --> DB[("PostgreSQL")]
  S -->|"GET /v1/postcode/{pc}/{nr}"| WCS["WCS Address API"]

Docker: api op poort 8000, database alleen intern, live-gateway via --profile live. Optioneel ngrok voor een fysieke telefoon.

2. Wie doet wat

GPT-Live (het model)

  • Groet in het Nederlands, daarna de taal van de bewoner; niet terugschakelen.
  • Spraak-in en spraak-uit over WebRTC.
  • Transcriptie (STT) en spraaksynthese (TTS).
  • Delegeert feiten, adres en bevestigingen naar de backend.
  • Leest de backendvraag hardop voor. Zoekt zelf geen adressen op.
  • Zegt niet dat de melding is opgeslagen tot de backend De melding is vastgelegd. stuurt.

Backend (bron van waarheid)

  • Houdt het intakedossier bij (JSON-document + revisie).
  • Haalt LEDO-velden uit de tekst (heuristiek, geen extra LLM).
  • Parst gesproken postcodes en belt WCS.
  • Bepaalt de volgende vraag via de beslisboom.
  • Schrijft de echte samenvatting en maakt het report.

Android toont het dossier, start WebRTC, en pollt de intake elke 700 ms zodat LEDO tijdens het praten meeloopt. De app belt GPT-Live niet zelf voor analyse.

Begroeting

Alleen instructions bij het aanmaken van de sessie is niet genoeg: het model gaat dan niet vanzelf praten. Na session.started stuurt de worker (en als fallback ook Android) daarom:

  1. session.instructions.append — “zeg dit exact, pauzeer daarna”
  2. wacht op session.instructions.appended
  3. session.commentary.append — “zeg nu hardop tegen de bewoner: …”

De gesproken zin is altijd huurwoning, nooit de vraag huur/koop. Als er al audio loopt, slaat de worker een dubbele groet over.

5. Eén gespreksbeurt

Elke keer dat de bewoner iets relevants zegt, delegeert GPT-Live naar de client. De worker heeft het transcript al opgebouwd uit session.input_transcript.delta. 

sequenceDiagram
  participant B as Bewoner
  participant G as GPT-Live
  participant W as live-gateway
  participant I as IntakeService
  participant WCS as WCS Address API

  B->>G: spraak
  G->>W: input_transcript.delta (accumuleren)
  G->>W: session.delegation.created target=client
  W->>G: session.thinking.append
"Backend werkt het dossier bij. Wacht."
  alt leeg transcript
    W->>G: commentary: wacht, stel geen nieuwe vraag
  else er is tekst
    W->>I: runAnalysis(transcript)
    I->>I: HeuristicIntakeAnalyzer + beslisboom
    opt postcode + huisnummer compleet
      I->>WCS: GET /v1/postcode/{pc}/{nr}
      WCS-->>I: 0, 1 of meer kandidaten
    end
    I-->>W: next_question.text
    alt dezelfde vraag als daarvoor
      W->>G: commentary: herhaal niet woordelijk, vraag anders
    else nieuwe vraag
      W->>G: commentary: zeg de vraag in de taal van de bewoner
    end
  end
  G->>B: gesproken vraag

Na de delegatie wordt het lokale transcript leeggemaakt. De volgende beurt begint opnieuw. Spraak legt geen IntakeMessage van de bewoner vast; alleen het dossier wordt bijgewerkt.

6. AI-calls en “tools”

Er zijn geen OpenAI function tools. Geen JSON-schema voor lookup_address of save_field. Het enige koppelpunt is client-delegatie.

Call 1 — sessie aanmaken

POST https://api.openai.com/v1/live/sessions
OpenAI-Beta: live=v1

{
  "session": {
    "model": "gpt-live-1",
    "instructions": "<conversation-v7>",
    "delegation": { "type": "client" }
  },
  "transport": { "type": "webrtc", "sdp": "<offer van de telefoon>" }
}

Call 2 — sideband (WebSocket)

WSS wss://api.openai.com/v1/live/sessions/{id}/attach

Events die de worker gebruikt:

EventRichtingFunctie
session.startedvan GPT-LiveSessie klaar; groet mag
session.instructions.appendnaar GPT-LiveExtra instructie (groet)
session.instructions.appendedvan GPT-LiveAck; daarna commentary
session.commentary.appendnaar GPT-Live“Zeg dit hardop”
session.thinking.appendnaar GPT-LiveWacht, backend is bezig
session.input_transcript.deltavan GPT-LiveSTT-stukjes van de bewoner
session.output_transcript.deltavan GPT-LiveWat het model zegt (alleen log)
session.delegation.createdvan GPT-LiveDe enige tool
session.closedvan GPT-LiveEinde

Call 3 — sessie sluiten

POST https://api.openai.com/v1/live/sessions/{id}/close

Wat de delegatie wél en niet is

  • wel Het model stopt even en zegt: dit is werk voor de client/backend.
  • wel De worker koppelt daar het verzamelde transcript aan en draait IntakeService::runAnalysis.
  • niet Het model krijgt geen tool-resultaat als JSON terug. Het krijgt een zin in commentary: de volgende vraag die het hardop moet zeggen.
  • niet WCS wordt nooit door GPT-Live gebeld. Alleen de PHP-backend belt WCS.

Prompt (conversation-v7), kernregels

  • Altijd huurwoning; nooit huur/koop vragen.
  • Groet in het Nederlands; daarna de taal van de bewoner (EN/DE/TR/JA). Niet terug naar Nederlands.
  • Eén korte vervolgvraag. Geen kamers, onderdelen of oorzaken verzinnen.
  • Postcode = 4 cijfers + 2 letters; cijfers als woorden; letters via spelalfabet (Simon Johan = SJ).
  • Adreslookup delegeren. “Klopt”, “ja”, “oké” zijn bevestigingen — meteen delegeren.
  • Samenvatting van de backend voorlezen. Niet zeggen dat het is opgeslagen tot De melding is vastgelegd.
  • Geen reparatie-advies, geen “monteur gestuurd”, geen planningstijd.

De analyzer verzint nooit een technische oorzaak. Onbekend mag. Vermoedens (“ik denk…”) worden hypothese, geen feit.

8. Postcode, huisnummer en WCS

GPT-Live spreekt alleen. DutchPostcodeParser maakt er 3573 SJ + huisnummer van. Daarna belt WcsAddressProvider de Address API. Fake BAG-straten worden in live nooit getoond (fake provider alleen in tests).

9. Samenvatting en de melding vastleggen

flowchart TD
  V["Adres verified + LEDO compleet"]
  W["writeSummaryDocument
SummaryComposer maakt resident_text"]
  Q["Vraag: {samenvatting} Klopt dit?"]
  Y{"ja / klopt / oké"}
  C["confirm → Report-rij in Postgres"]
  D["De melding is vastgelegd."]
  LOOP["Boomtekst: Ik vat het probleem samen...
zonder summary-document"]

  V --> W --> Q --> Y
  Y -->|ja, summary bestaat| C --> D
  V -.->|als summary niet wordt geschreven| LOOP

SummaryComposer maakt iets als: Badkamer: Kraan Lekt. Oorzaak onbekend. De bewoner moet die tekst bevestigen. Daarna ontstaat één Report.

Afronden. Als de boom op terminal_summary staat, schrijft de backend de echte samenvatting ({tekst} Klopt dit?) en maakt bij ja / klopt / rond af het report. Daarna: De melding is vastgelegd. De plaatshouderzin van de boom mag het gesprek niet laten hangen.

11. Android

  • Activatiecode → Bearer-token (POST /api/v1/auth/activation).
  • Start intake → eventueel voice-session met SDP-offer.
  • Fake-SDP van de backend wordt niet op WebRTC gezet (voorkomt crash).
  • watchIntake pollt 700 ms; SSE bestaat op de API maar de app gebruikt het niet.
  • Speakerphone, gain 1.0. LEDO-scherm volgt het dossier tijdens het gesprek.

Wat expres niet gebeurt

  • GPT-Live belt WCS of PDOK niet.
  • PDOK zit niet meer in de code; altijd WCS.
  • Geen function-calling tools.
  • Geen automatische adresverificatie zonder ja/klopt van de bewoner.
  • Geen secrets in git.
